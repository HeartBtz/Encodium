## Compatibilite et migrations

- Pas de suppression/renommage de colonne introduit. `file_size_after` et
  `finished_at` restent disponibles ; les valeurs sont copiees vers les colonnes
  modernes vides, dans une transaction, avec un marqueur dans `settings`.
- Les migrations precedentes ALTER de l'application restent presentes et peuvent
  verrouiller les tables au boot. Les erreurs autres que colonne deja existante
  ne sont plus masquees. Prevoir sauvegarde et fenetre de maintenance avant toute
  execution en production ; dump et historique reel non inspectes ici.
- Aucun TRUNCATE dans le nouveau `clearAll`. Clear reste explicitement destructif
  pour videos/jobs/savings/presets, mais n'est pas lance automatiquement et refuse
  des jobs outstanding. Users/settings/sources et auto-increments sont conserves.
- JSON des presets/jobs, endpoints et formes principales des reponses conserves.
  Changements de securite intentionnels : enqueue/logs admin, valeurs invalides
  refusees, delete job actif/pending refuse, cancel attend sa mise a jour DB,
  chemins hors roots/symlinks refuses. Les anciens chemins DB ne sont pas reecrits.
- Nouvelles copies non remplacantes : nom avec ID du job, source reste indexee.
  Aucun renommage des sorties existantes. Les statistiques de savings restent un
  ledger de rendement d'encodage, pas une mesure de liberation physique du disque
  lorsque l'original est conserve.
- Une annulation apres le point de publication est refusee : `cancelled:false`
  ou erreur de finalisation pour force-kill. Ne pas retirer un job avant la fin
  du worker. La nouvelle tolerance de duree peut refuser des medias aux timestamps
  pathologiques plutot que risquer un remplacement incomplet.

## Risques restants et hors test

1. **P1 avant toute mise en production, parent** : verifier Host/Origin effectifs,
   source IP du proxy, ecrasement des forwarded headers, CORS_ORIGINS exact et
   COOKIE_SECURE. TRUST_PROXY vide peut agreger les utilisateurs derriere un
   proxy dans le meme quota IP. Le cas HTTPS Origin + upstream HTTP + cookie
   Secure passe en fixture ; aucun domaine/proxy reel inspecte ou suppose ici.
2. **P2 supervision** : aucune recherche/termination globale de processus. Le
   superviseur doit arreter les enfants appartenant au service ; anciens orphelins
   et fichiers temporaires de crash necessitent une revue operateur. Aucun test
   de restart PM2/systemd, OOM, signal reel d'un encode long ou nettoyage production.
3. **P2 filesystem/DB** : aucune transaction atomique commune entre media et SQL,
   ni garantie de durabilite apres coupure electrique/fsync. Staging exige espace
   et I/O supplementaires ; hardlinks requis pour les nouvelles destinations.
   NFS/CIFS, quota/disque plein, panne pendant copie, ACL/ownership et crash au
   commit non testes. Bits de mode Unix preserves, pas les ACL ou proprietaires.
   Race locale hostile sur un repertoire parent apres realpath non eliminee.
4. **P2 file/charge** : anti-doublon du frontend et serialisation par video dans
   un processus ne sont pas une cle d'idempotence globale. Enqueues independants
   concurrents peuvent encore creer des jobs repetes. Plusieurs encodeurs sur
   une meme DB ne sont pas valides. Rate limits en memoire/par IP, pas de defense
   distribuee ni agregation IPv6 /64 ; refresh hardware simultanes non dedupliques
   (`services/gpu-detect.js:82`). Journaux disque sans rotation interne.
5. **P2 sessions** : logout supprime le cookie, pas un JWT copie. Pas de revocation
   individuelle au changement de mot de passe ; duree maximale sept jours. Roles
   et suppression de compte sont verifies, SSE peut rester ouvert jusqu'a 30 s
   avant revalidation. Pas de test temporel long de cette revalidation.
6. **P2 fonctionnalites encore incompletes** : le catalogue GPU/CPU ne propose pas
   de preset H264 malgre sa validation dans les custom presets
   (`services/gpu-detect.js:67-73`, `:123`). `extra_args` est stocke mais non execute
   (pas un shell configurable). Le smart skip par codec de `enqueue`/`enqueueBatch`
   reste prioritaire sur force/downscale/tonemap pour un fichier deja au codec
   cible (`services/encoder.js:1198`, `:1264`). Ces limites sont signalees, pas
   masquees comme fonctionnalites validees.
7. **P2 media non fiables** : pas de sandbox OS FFmpeg ; whitelist reseau n'interdit
   pas toutes les lectures locales secondaires d'un demuxer. Admin reste une
   autorite de configuration du filesystem via sources/browse. Pas de validation
   exhaustive des demuxers, corruption, attachments, sous-titres, HDR/DV, NVENC,
   QSV, VA-API, multi-GPU ou qualite visuelle. Arguments GPU testes sans hardware.
8. **Limites de mesure** : API DB en partie simulee, worker subprocess simule sauf
   petit encode CPU separe. Pas de suite E2E unique mariant GPU+DB+browser,
   end-to-end webhook public/TLS, charge longue/SSE lent, Firefox/WebKit ou
   installation runtime non-root. Warning express-rate-limit attendu lors du
   test X-Forwarded-For falsifie avec trust proxy=false ; le 429 est bien observe.

Les controles existants utiles (bcrypt, HS256, cookie HttpOnly/SameSite, CSP,
SQL parametre, range borne, DNS webhook epingle, garde taille et mounts) ont ete
conserves. Ce rapport ne transforme ni leur presence ni les tests verts en preuve
de recuperabilite de sauvegardes ou d'absence de toutes vulnerabilites.
